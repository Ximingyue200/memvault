## P0 — 影响检索可信度

### 1. 原文重复 26.6%（14,466 条）

```
spans 总数       54,430
唯一 text_hash   39,964
重复             14,466  (26.6%)
重复组           7,037
```

最严重的几组：

| 次数 | 内容片段 |
|---:|---|
| 3,635 | `# .xcl 两种主流类型用法 ## 类型1：IAR嵌入式链接配置文件…` |
| 238 | `你好呀，欢迎回来。你还有更多想了解的吗？` |
| 213 | `---` |
| 147 | `(no output)` |
| 93 | `ssh_exec failed: No response from server…` |

**根因**：cradle 导入时的切分算法对超长文本按固定字数硬切，切出的每一片 `text_hash` 相同，没有做合并。3,635 次那组就是一段 `.xcl` 文件格式说明被切了 3,635 片。

**影响**：检索时同一段内容会占满召回名额；存储浪费约 26%。

**建议**：按 `text_hash` 保留一条（优先保留 `ts` 非空的），其余删除并重指 `card_evidence`。或在切分阶段就做 hash 合并。

### 2. 证据链断裂 12.2%（2,357 条）

```
card_evidence 总数        19,290
指向不存在 span 的        2,357  (12.2%)
```

**根因**：早期清理 span 时没有级联删除对应的 `card_evidence`。

**影响**：这些证据点在 UI 上点开是空的；`/find` 返回的「原文引用」可能 404。

**建议**：`DELETE FROM card_evidence WHERE span_id NOT IN (SELECT span_id FROM spans)`，或重新指向同 hash 的其他 span。

### 3. 无证据卡 649 张（5.1%）

**根因**：cradle 早期导入的卡从源头就没记 `source_range`（曾查过 `SELECT source_range FROM cards`，6,867 张全空）。

**影响**：这 649 张卡无法回溯原文，只能当「无据推断」看待。

**建议**：标 `claim_type='inferred'` 或在 UI 上区分展示，不要与有证据的卡混排。

## P1 — 影响数据质量

### 4. `cards.kind` 七种值并存

```
definition  5,083   40.3%
fact        2,967   23.5%
event       2,665   21.1%
experience  1,171    9.3%
preference    426    3.4%
tool          305    2.4%
note            5    0.0%
(空)            1
```

`store.KINDS = ("definition", "event", "note")` 只认 3 种；`LEGACY_KIND_MAP` 把 `fact / entity / rule / tool / profile / preference` 全映射成 `definition`。

新卡走 `normalize_kind` 故只有 3 种，旧卡是 cradle 导入时直接写库、没走 normalize，所以保留了原值。

**影响**：`WHERE kind='fact'` 查不到 5,083 张 definition；`WHERE kind='definition'` 查不到 2,967 张 fact。语义上 `fact` 和 `definition` 是同一件事（稳定陈述）。

**建议**：一次性 `UPDATE cards SET kind='definition' WHERE kind='fact'`，或反过来把 definition 拆开。前提是先确定检索侧有没有硬编码 kind 值。

### 5. 重复卡片 184 组 / 冗余 204 张

```
3x  豆包导出结果数字
3x  记忆库骨架上午已建好，缺血肉
3x  自动提炼把明文密码写回搜索区
3x  自动提炼写不出梦境层
3x  某迷你主机接口配置
3x  方向稿落盘路径
3x  摘老插件前必须补 bootstrap
3x  拒绝代过滑块验证
```

**根因**：`cards.content_hash` 只防完全相同的正文，防不住「换标题改写同一件事」。

**建议**：用 `vectors` 做相似度合并（阈值 0.92 以上视为同一张）。

### 6. `cards.importance` 全库一个值

```
{5: 12646}
```

**影响**：这个字段没有任何区分度，等于没做。排序、加权、注入优先级都用不上它。

**建议**：要么删掉这个字段，要么接入一个真实的打分（热度 × 证据数 × 被召回次数）。

### 7. 正文过短 660 张

```
< 60 字   660 张
< 30 字    19 张
最短       18 字
```

**影响**：这类卡基本是「一句话结论」，没有上下文，检索时容易误命中。

## 新问题 P0-0：learn 产出的 953 张几乎全是废卡

跑完后抽检最近 20 张，全部是「这次调试做了什么」的现场记录：

```
[13650] 请求导出对话        "用户发出指令「导出所有的对话」…"

[13644] 库最新数据时间       —
[13643] 门槛0.55剩2条        —
[13642] 检索12条5619字       —
[13641] 固定注入899字        —
```

### 三个量化结论

1. **97.3% 的卡正文以「原文：」开头**（977 / 1,004）—— 模型把证据片段抄进了 `content`。
2. **标题重复极重，TOP20 占 114 张**：`文件策略全权限 17` / `工作目录路径 17` /
   `引擎代码路径 11` / `当前工作目录 6` / `Web GUI 端口 3080 6`。
   **全是 DSH 的 `AGENTS.md` 系统提示被反复提取。**
3. **正文含环境词**：`danger-full-access 57` / `3080 45` / `openclaw 25`；
   含真技术词的反倒少：`PVE 52` / `7840HS 11` / `bge-m3 6` / `LXC 6`。

### 两条被证伪的假设

- **不是噪声污染**：新增 1,004 张里正文含运行时噪声的只有 **3 张**；
  全部 spans 含 `Runtime: agent=` / `Conversation info:` / `⟦openclaw:` 的只有
  **18 / 54,430 = 0.0%**，2026-11 区间 **18 / 1,750 = 1.0%**。`collect.py` 的清洗有效。
- **不是 `occurred_at` 缺失导致内容错**：只是元数据缺失，不影响正文质量。

### 真根因

`extract()` 的 PROMPT 没有区分「**可复用知识**」与「**本次操作记录**」。
DSH 会话本身是「AI 干活 + 用户下指令」的过程记录，提取器把过程当成了结论。
补丁上还缺两条：模型会抄原文、会提取系统提示。

## 修复：PROMPT 加六类拒绝清单（提交 57b5498）

旧 PROMPT 只有 7 条规则（落在具体东西上 / 禁止抽象化 / 一条一件事 /
保留踩坑 / 类型五选一 / 代写作业返回 [] / AI 范例文本返回 []）。

新增六类**绝对拒绝**：

| 类别 | 内容 | 反例 |
|---|---|---|
| A | 运行时环境与上下文 | 工作目录、`danger-full-access`、端口 3080、hostname、AGENTS.md 里的规定 |
| B | 一次性观测数字 | 「检索返回 12 条共 5,619 字」「49.1k 字 1060ms」「门槛 0.55 剩 2 条」 |
| C | 操作动作与指令 | 「用户要求导出对话」「执行了某命令」「用户说按你说的来」 |
| D | 本系统自身调试记录 | 「某表是某天的快照」（例外：写出可复用判据的） |
| E | 用户对 AI 的元评价 | 「这个方案好」「继续」「两个一起」 |
| F | 只有「记住这次做过什么」价值的 | — |

新增规则 8：`content` 里不要抄原文、不要写「原文：」前缀、不要用引号包裹对话片段，
用自己的话写成陈述句。
