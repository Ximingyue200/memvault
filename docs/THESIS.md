# 能不能当本科毕业设计：一份冷静的评估

> 结论先说：**够格，但现在还只是"做完了"，不是"证明了"。**
> 时间上距毕业还有一年，不急，先存档判断标准。

## 1. 四维体检

| 维度 | 现状 | 判断 |
|---|---|---|
| 工作量 | 约 1.5 万行 Python / 115 文件 / 22 张表 / 两套协议（OpenAI + MCP）/ 面板 26 页 / 部署脚本 | 超过一般本科，甚至偏大 |
| 技术难度 | 混合检索融合、交叉编码器重排、span 级证据链、热度衰减、写入治理（队列/判重/取代）、多 agent 身份 | 中上，够撑 |
| 创新性 | **弱**。bge-m3、reranker、RRF、BM25 都是现成件；融合权重 0.65/0.35 是经验值 | 短板所在 |
| 规范性 | 有 DDL、有 CI、有部署文档、有压测记录、有 bug 台账 | 反而是加分项 |

一句话：**工程分很高，研究分不足。**

## 2. 选题口径

建议题目：**《面向多 Agent 协作的本地长期记忆中间件设计与实现》**

三个可辩护的贡献点（都已实现，不需编造）：

1. **写入治理**：agent 写入天然碎片化且会互相污染。提出「暂存队列 + 相似度三档（≥0.93 判重 / 0.80–0.93 取代 / 其余新建）+ 改主意识别」的写入管线，用 token 绑定身份，解决"最后写入者永远赢"。
2. **可溯源检索**：卡片 → 证据 span → 原始字符区间的三级回查；配合热度半衰期与取代降权的融合打分。
3. **双模态接入**：同一记忆核心同时以"透明网关（自动注入）"与"MCP 工具（自主调用）"暴露，验证换 agent / 换模型后记忆是否连续。

第 1 条最有论文味——它对应一个真实缺陷，且有前后对比数据（假话顶掉真话 → 取代后命中正确版本）。

## 3. 评价指标（按应用端口径）

应用端方案的评价不看"召回率高几个点"，看系统行为：

| 维度 | 指标 | 现有数据 |
|---|---|---|
| 一致性 | 冲突写入后命中正确版本的比例 | 改造前：假话压过真话；改造后：取代链生效 |
| 冗余率 | 同一事实平均存几张卡 | 治理前出现过 1 分钟 16 张近似卡 |
| 接入成本 | 接入一个 agent 需要改几处 | 网关类改 base_url 一行；MCP 类填一个 URL；OpenClaw 改 provider + header 两处 |
| 零侵入 | 是否改客户端源码 | 全部为配置项 |
| 可运维性 | 故障是否降级、队列是否可见 | fail-open 已实现；面板有队列深度与 agent 分布 |
| 成本 | 每次写入 / 每轮对话的花费 | 已建记账（按任务与 key 拆分） |

精度仍然要报，但它是配角。

## 4. 必须补的三组实验

### ① 主实验（检索质量）
- 数据：从真实库中人工标注 300–500 条事实 + 100–150 个查询（每题 1–3 个正确答案）。
- 基线：纯向量 top-k / 纯 BM25 / 向量+BM25 无重排 / 有重排无衰减 / 完整系统。
- 指标：Recall@5、MRR、nDCG@10、注入 token 数、平均延迟。

### ② 消融（证明每个部件有用）
逐个去掉：暂存队列、判重、取代、常驻层、热度衰减，各跑一遍①。

### ③ 写入治理专项
构造 50 组冲突（同一事实改主意 / 两个 agent 说反话），统计：冗余卡率、错误取代率、最终命中正确版本的准确率。

加分项：50 并发写入吞吐、冷启动建库时间、每千次写入成本。

## 6. 三个风险

1. **借鉴要写清楚**：Hindsight / Mem0 / Letta / OpenViking / BM25 / RRF 均已在 README 致谢，论文需单开一节写"与现有工作的关系"。不要声称完全自研。
2. **代码查重**：项目已开源，写明"本人开源，提交版本见 commit xxx"即可，但要确认学校对公开仓库的规定。
3. **工程型选题需导师点头**：多数学校认可，部分要求必须有算法对比。开题前先确认"工程实现为主 + 定量评估"是否可行。
