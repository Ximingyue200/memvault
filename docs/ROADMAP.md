# 发展路线：从单体到蜂巢

> 状态：设想，尚未动工。写下来是为了先把边界讨论清楚，避免边写边改架构。
> 定位前提：本系统站在**应用端**（谁在用模型的那一端），不在模型端。
> 当前最大风险：**库是单点**。它一挂，所有 agent 的记忆同时变哑（只剩 fail-open 空转）。容灾见第 7 节。
> 愿景与思想稿见 [VISION-hive-gestalt.md](VISION-hive-gestalt.md)；本文只讲落地切分与待拍板项。

## 0. 一句话

一个库、多只工蜂；蜂巢是共享底座，格式塔是从共享里**算**出来的整体。

## 1. 两个词分别对应什么机制

| 概念 | 工程含义 | 现状 |
|---|---|---|
| 蜂巢 | 共享存储 + 多 agent 并发读写 + 身份与分工 + 留痕 | 雏形已有：`cards.owner`、`api_tokens`、`pending` 互看 |
| 格式塔 | 跨 agent 的**共识层**：这群 agent 共同认定的事实、各自的专长、当前在做什么 | 缺。`scope` 只有 global/project/agent/session |

结论：格式塔不是"存出来的"，是"算出来的"——从多 agent 的独立写入里提炼，而不是把各自的卡堆在一起。

### 共识层的最小设计

- 判据：同一事实被 **≥2 个不同 token 独立写入**（不是复述已有卡）+ 各自带 span 证据 + 时间窗内。
- 存储：`cards.scope` 增加取值 `hive`，或新增 `cards.consensus smallint`（0/1/2，2=多源确认）。
- 注入顺序：`hive` 共识 → `global` 事实 → `agent` 个体 → `session` 临时。
- 反例要挡住：A 抄 B、B 抄 A 会被误算成两票——所以判据必须是「独立来源」，需要记录每张卡的 `source_agent` 与证据 span 来源。

## 2. 主体与插件的切分

判断标准只有一条：**换掉它，库里的数据要不要迁移？**

- 要迁移 → 留在核心里（拆不动）
- 不要迁移 → 插件

### 核心（不可拆）

1. 存储与 schema（原文 / 卡片 / 证据 / 向量）
2. 写入管线（队列 → 判重 → 取代 → 落卡）——唯一的一致性保证点
3. 身份与权限（token、scope、可见性）
4. 检索入口（单一 `search()` 契约）

### 七个插件位

| 插件位 | 对应现有实现 | 可替换为 |
|---|---|---|
| 采集器 | `collect.py` | 对话流 / 文件 / 网页 / 其他 agent 日志 |
| 抽取器 | `extract.py`、`demoextract.py` | 换模型、换 prompt、换本地小模型 |
| 打分器 | `search.py` 的融合与衰减 | 换权重、学习排序、时间策略 |
| 注入器 | `gateway.py` 的块拼装 | 卡片式 / 摘要式 / 结构化 JSON |
| 渲染器 | `admin-panel/` | 换 UI，或只留 API |
| 适配器 | 网关、MCP | 见第 3 节 |
| 导出器 | `mvbackup.sh`、`/export` | 文件 / S3 / 另一个库 |

## 3. 适配器四档（按侵入程度）

| 档 | 形态 | 接入条件 | 现状 |
|---|---|---|---|
| A | 透明代理，改 `base_url` | 客户端支持自定义 OpenAI 兼容地址 | 已完成（`:4180` 注入 / `:4182` 不注入） |
| B | 协议适配（MCP） | 客户端是 MCP client | 已完成（`:4181`，7 个工具） |
| C | 原生插件（用对方插件 API） | 客户端有插件机制 | 未做。价值不在"能接"，在于能拿到会话开始/结束、工具调用前后、当前工作目录等事件 |
| D | 伪装（实现对方期望的记忆后端 API） | 对方把记忆后端当可替换组件 | 有先例：4175 的 OpenViking shim。**最脆的一档** |

### C 档优先对象

- **OpenClaw（龙虾）**：正在用、有插件 API、能拿事件 → 首选
- DSH：`cordis.patch.yml` 有注入点
- 其他带插件机制的 agent：按需

### D 档的真实代价

1. **契约漂移**：对方改一个字段名，shim 静默返回空——与「外部依赖静默失效」是同一类故障。
2. **语义错配**：多数上游 `add/search` 要求即时返回，而队列是延迟落卡。
3. **责任错位**：伪装得像，用户会把记忆不准算在对方头上，你拿不到日志。
4. **维护成本**：每加一个 D 档适配器 ≈ 每季度一次修补。

建议：D 档只做「接口极稳定」或「已停更」的对象；活跃迭代的走 C 或 B。

## 4. 蜂巢的三个硬问题

1. **写污染**：全局余弦 0.93 判重会让同一事实的不同侧面互相吞掉。判重应限定在同一 `subject` 内，而非全局。
2. **共识形成**：不能靠票数（agent 没有可信度），要靠「独立性 + 证据 + 时间窗」；否则形成回声室。
3. **身份泄露**：`pending` 对所有 agent 可见是协作的前提，也是泄露面。需要可见性级别（如 `public-to-agents` / `private-to-token`），而不是全开。

## 5. 待拍板（三项决定后续实现）

1. 共识层现在做还是等后面？——决定 schema 要不要再动一次。
2. 插件进程内还是进程外？——倾向进程外（HTTP/stdio，各自崩溃隔离），代价是多一层序列化。
3. C 档先做龙虾还是先做通用插件宿主？
4. D 档保留几个？——建议只保留「OpenAI 兼容」这一个。
5. `/admin` 鉴权是否与插件体系一起做？——插件一多，裸面板会成为被扫的入口。

## 6. 不做什么

- 不做模型端记忆（训练、微调、厂商内置），只做应用端。
- 不做第二套 UI。
- 不为单个 agent 写死逻辑，一律走适配器。

## 7. 容灾：主脑 / 副脑

两台机器各跑一套 agent + memvault，一个主脑、一个副脑。技术上真正的难点只有一个：**库怎么同步**。agent 是无状态的客户端，切换只是改 `base_url` 与 token。

### 三种成熟度，别一次做完

| 级别 | 做法 | RPO / RTO | 能扛 |
|---|---|---|---|
| L1（已有） | `mvbackup.sh` 每日全量 + 异地一份 | 24h / 十分钟级 | 误删、坏库、单文件损坏 |
| L2 | 单向 WAL 热备 + 只读副脑 + 手动升主 | 秒级 / 分钟级 | 主机宕机、维护窗口 |
| L3 | 双活 + HLC + fencing | 秒级 / 秒级 | 两地都要写 |

**L2 就够用。** 需求是"主脑挂了副脑顶上"，不是"两台同时写"。L3 复杂度约是 L2 的五倍，而 agent 无状态让它的收益很小。

### L2 要点（推荐）

- 传输对象是 **WAL 增量 / 逻辑操作流**，不是整库 rsync（226MB 全量太重）。
- 副脑持只读副本，可对外提供降级读。
- 切换步骤：副本提升为可写 → 改 agent 的 `base_url`（4180/4181）→ 副脑接管 learn/dream 定时任务。
- 副脑的读是"旧读"：落后 N 秒时会少看到最近写入。响应里带 `lag_ms` 让调用方知情，或直接接受。

### L3 要点（暂不做，但先把约束写死）

1. **时钟**：用 HLC（混合逻辑时钟），不用 `datetime.now()`；否则两台机器时间差几分钟就判错新旧。
2. **脑裂**：主脑没死但网络断，副脑以为它死了自己升主 → 两边都写 → 合并必炸。必须 **fencing**：升主时领一个单调递增的 `generation`，旧主带旧 generation 的写入一律拒绝。
3. **不该同步的东西**：`api_tokens`（每台自己的身份）、`settings`（端口/路径是本机的）、`.qflush.lock`、pids —— 同步过去会把对方搞坏。
4. **冲突消解可复用**：`cards` 近似不可变（改主意走 `supersedes` 新卡），天然 append-only；判重 0.93 / 取代 0.80 / 权威分级已具备；`content_hash` 可直接做集合去重。

### 插件契约（第四个插件位之外的单列一项）

```
role()              -> primary | standby
push_ops(since)     -> 推操作流
pull_ops(since)     -> 拉操作流（仅双活用）
health()            -> peer 延迟 / 落后条数 / 最后心跳
promote(generation) -> 升主，返回 fencing token
```

配置项：`sync.peer_url`、`sync.role`、`sync.lease_seconds`（建议 30）、`sync.mode`（mirror | dual）。

### 两个必须能回答的指标

- **RTO**：从主脑挂到副脑可写、agent 改完地址，实际用了多少分钟。
- **RPO**：最坏情况丢多少秒的写入。

没有这两个数字，就不算有容灾，只算有备份。
